# space-chat: storage engine design

Sub-project 3 of 5 in the space-chat initiative. Covers local, per-device persistence for the epoch-segmented Automerge docs, MLS state, attachments, and the derived views (listing/pagination, search) the UI reads from. Builds directly on [the protocol & sync design](2026-09-03-protocol-and-sync-design.md).

## Goals

- Local persistence survives restarts and is resilient to partial corruption of any derived (non-authoritative) state.
- The primary conversation-viewing path is always synchronous and immediately consistent — a message you just sent must appear instantly, with zero tolerance for staleness.
- Full-text search works across conversation history, with staleness of at most a short near-real-time delay being acceptable.
- Attachment storage deduplicates identical content and reclaims space for content nothing references anymore, without risking deleting content another peer still needs.
- Implementations are swappable behind trait boundaries defined in `space-chat-core`, following the same contract-first pattern retrofit-ui itself uses (`packages/core` defines the interface, other packages implement it).

## Crate layout

- **`space-chat-core`** — defines all trait boundaries this spec introduces (`SegmentBlobStore`, `AttachmentBlobStore`, `ListingIndex`, `SearchIndex`, `AttachmentMetadataStore`) plus the segment/epoch management and Automerge sync logic that consumes them. No dependency on `redb`, `tantivy`, or `openmls`.
- **`space-chat-storage-redb`** — implements `ListingIndex` and `AttachmentMetadataStore` using `redb`.
- **`space-chat-search-tantivy`** — implements `SearchIndex` using `tantivy`.
- **`space-chat-openmls`** (sub-project 2, referenced here) — implements OpenMLS's own `StorageProvider` trait directly against `redb`. This is *not* exposed through `space-chat-core`'s trait surface — it's an internal detail of how that crate satisfies an external trait OpenMLS itself requires, not something the rest of the system needs to know about. `space-chat-app` decides at composition time whether this shares a physical `redb::Database` handle with `space-chat-storage-redb` or uses a separate file.
- Segment and attachment bytes are **not** behind `redb` or `tantivy` at all — they're plain content-addressed files on disk (see below).

**Why `redb` and `tantivy` specifically, over SQLite (+FTS5)**: both are pure-Rust, with a materially smaller unsafe-code surface than SQLite, which is a large, mature C library reached through an FFI boundary via `rusqlite`. This was a deliberate choice, not just "what's convenient" — see the consistency tradeoff below for what it costs.

## Data placement

| Data | Where | Authoritative? |
|---|---|---|
| Automerge segment bytes | Flat file, `segments/<space_id>/<epoch>.automerge` | Yes — source of truth |
| Attachment bytes | Flat file, content-addressed (`attachments/<hash prefix>/<hash>`), git-object-store style | Yes — source of truth, and irreplaceable (no hash→bytes reconstruction) |
| MLS state (keys, group state, epoch secrets) | `redb`, via OpenMLS's `StorageProvider` | Yes — irreplaceable, not derived from anything else |
| Listing/pagination index (ordered by `(space_id, epoch_index, seq)`) | `redb` | No — derived, rebuildable from segments |
| Attachment metadata (hash → size/mime) + GC liveness bookkeeping | `redb` | No — derived, rebuildable from segments |
| Full-text search index | `tantivy` | No — derived, rebuildable from segments |

Three things are irreplaceable (segment bytes, attachment bytes, MLS state) and everything else is a disposable projection that can be regenerated by replaying segments.

## Why listing/pagination is `redb`, not `tantivy`, despite both being viable

Tantivy supports sorted, paginated range queries via fast fields, so `space_id:X` sorted by a `timestamp` fast field is a real, working pattern — this isn't a capability gap. The reason it's the wrong choice for the primary conversation-listing path specifically: **Tantivy is near-real-time, not immediately consistent.** Writes aren't visible to reads until a commit/refresh cycle. That's an acceptable, expected latency for search — nobody minds if a just-sent message takes a second to become searchable. It's not acceptable for the view you land on when you open a conversation: the message you just sent must appear immediately, every time, with no exceptions. Routing the primary view through Tantivy would require a "read-your-own-writes" overlay (an in-memory buffer of unsearched-but-just-created messages merged on top) purely to paper over a gap `redb` doesn't have in the first place, since it commits synchronously.

This also keeps the two derived views' failure/staleness tolerance appropriately separated: search is allowed to be briefly out of date or rebuilding; the primary conversation view is not. Conflating them into one subsystem would mean a search-index rebuild or corruption blocks basic conversation viewing, not just the search box — a bigger blast radius than the design intends.

## Consistency tradeoff: no shared transaction across `redb` and `tantivy`

SQLite+FTS5 (via the standard external-content-table-plus-triggers pattern) gives real ACID atomicity between a content row and its search index entry, because both live in the same file under the same transaction log. `redb` and `tantivy` are two independent storage engines with separate commit protocols — there's no way to atomically write to both, which is the standard **dual-write problem**. A crash between the two writes can leave them briefly diverged.

This is judged acceptable here because neither store is a source of truth — both are derived, rebuildable projections of the same immutable, append-only segment log (this was true even under the SQLite design). The fix is a **watermark per projection**, not a cross-store transaction:

```
trait Projection {
    fn watermark(&self) -> SegmentCursor;  // last segment change incorporated
    fn apply(&mut self, change: SegmentChange) -> Result<()>;
}
```

`ListingIndex` and `SearchIndex` both implement this. On startup, each independently compares its watermark against what's on disk in `segments/` and replays forward whatever it's missing — the same event-sourcing pattern used by e.g. independent Kafka consumer offsets, requiring no distributed transaction. The one real, honest consequence: there's a window where a just-sent message is visible in the primary view before it's searchable. This isn't a *new* inconsistency — it's the same near-real-time gap already accepted when choosing Tantivy — it just means catch-up is something we build (the watermark) rather than something SQLite gave for free.

**There is a third `Projection` consumer, not just these two: the app-shell's spec-generation layer** (sub-project 5), for whichever conversation is currently actively viewed. It needs the identical "a new segment change arrived" signal `ListingIndex`/`SearchIndex` get, in order to know when to regenerate/patch the live `ConversationSpec` — this should be the same fan-out from `space-chat-core`, not a second, independently-invented notification path. Concretely: `space-chat-core` exposes one change feed; `ListingIndex` and `SearchIndex` always consume it for every space (see below), and the app-shell layer additionally subscribes to it only for whichever single space is actively displayed. **`ConversationSpec` generation should read its ordered message window from `ListingIndex` itself, not re-derive ordering from raw segments independently** — `ListingIndex` already owns exactly that ordering (`(space_id, epoch_index, seq)`), and rebuilding the same ordering logic a second time in the app-shell layer would be pure duplication with no benefit.

**`ListingIndex` and `SearchIndex` stay eagerly maintained for every space regardless of whether it's actively viewed** — a sidebar showing unread counts or a cross-space search needs both to be current for spaces nobody currently has open. Only the app-shell's live `ConversationSpec`/patch-emission is gated by "actively viewed," per the app-shell spec's bounded-window design. Worth stating plainly since the two "only do this for what's being looked at" ideas — bounded listing windows and active-view gating — apply at different layers and could otherwise be conflated.

## Attachment garbage collection

Attachments are content-addressed and deduplicated — the same file shared across conversations is one blob referenced by multiple `AttachmentRef`s. A blob can't be deleted the moment one reference is tombstoned; something else might still need it.

**The harder problem: local liveness ≠ global liveness.** A device only knows about references it has synced so far. If it computes "zero live references" and deletes, a peer that hasn't yet synced the tombstone — or is about to re-share the same content — can have that reference resurface with no way to recover the deleted bytes (content-addressed: no hash→bytes reconstruction). This is inherent to doing GC in a system with no server to ask "has everyone caught up," and no local storage engine choice changes that.

**Mechanism: periodic mark-and-sweep, not incremental reference counting.** Rather than maintaining a reference count incrementally (which risks drift — e.g. double-counting during a projection replay), run a full sweep on a cheap, frequent schedule (e.g. daily): walk all non-tombstoned `AttachmentRef`s currently reachable from local segment state and mark those hashes live. For each hash **not** marked live in a given sweep, record (or leave untouched, if already set) a `first_seen_unreferenced` timestamp; a hash that *is* marked live has that timestamp cleared immediately. A blob is only actually deleted once `now - first_seen_unreferenced >= 30 days` (the grace window) — i.e. it must have been continuously unreferenced across every daily sweep spanning the full window, not merely "unreferenced twice." Note this corrects an earlier inconsistency in this section, which described "two consecutive sweeps" against a daily cadence — literally two days, not the intended 30. A blob that comes back into a live reference before the window elapses just has its timestamp cleared — no separate cancellation logic needed, it falls out of re-running the same computation.

This is deliberately simpler than reference counting (no drift-prone incremental bookkeeping) and it's the right place to tolerate "batchy and eventually consistent," unlike the listing/search split above — GC has no user-facing immediacy requirement the way viewing a conversation does.

**Honest bound on the limitation:** if every peer holding a live reference is unreachable for longer than the full grace window, content loss is still possible when that peer eventually reconnects. This affects only attachments — messages/text persist forever in synced segments regardless — and only when *every* referencing peer is offline that long, not just one.

**"Reachable" here means reachable specifically for attachment transfer, which per the transport spec is strictly direct-endpoint — not the wider multi-hop reachability messages get.** A peer can be fully reachable for message/reaction/tombstone sync (via a hop through a third device) while still being unreachable for *this specific blob* if no direct-or-relay path exists to a peer that actually holds those bytes. Don't read "at least one referencing peer stays reachable" as "reachable in the same sense the sync engine means it" — it's a narrower, harder bar to clear, and the grace window exists partly to absorb that gap.

## Error handling

- **Listing/search index corruption or loss** — rebuild by replaying `segments/` from scratch. No data loss; just a temporary window of degraded search/listing while rebuilding.
- **MLS state loss** — not recoverable. That device permanently loses the ability to decrypt segments under old epochs; it can rejoin for future epochs via a fresh Welcome.
- **Segment or attachment file loss/corruption** — not recoverable locally; the device must re-sync that content from a peer that still has it, same as any other missing segment.
- **Projection watermark ahead of what's on disk** (e.g. a partially-written segment file from a crash) — detected via checksum/hash mismatch on the segment file; treated as if the segment were missing, re-fetched from a peer.

## Testing

Uses the shared multi-actor `cucumber-rs`+`fantoccini` harness defined in the app-shell spec's Testing section. Most storage-layer failures have no direct UI representation (a GC sweep or a watermark catch-up isn't itself rendered), so scenarios here mostly assert the **user-visible consequence** of a storage-layer event rather than internal store state directly — falling back to internal assertions only where there genuinely isn't one:

```gherkin
Feature: Attachment garbage collection respects cross-peer liveness

  Scenario: An attachment isn't lost if a peer holding the only other reference is offline within the grace window
    Given Alice and Bob share an attachment referenced only in one message
    And Bob goes offline
    When Alice deletes the message referencing the attachment
    And 20 days pass
    And Bob comes online
    Then Bob's conversation view still shows the attachment as available
```

- Kill-and-restart tests that interrupt writes mid-flight (segment file write, `redb` transaction, Tantivy commit independently): asserted via the actor's conversation view showing correct, complete history after restart, not by inspecting `Projection` watermarks directly.
- Mark-and-sweep GC timing itself (the `first_seen_unreferenced` bookkeeping, the 30-day threshold) has no UI outcome to assert and stays a direct unit test against `AttachmentMetadataStore`, run alongside the Gherkin suite.
- Rebuild-from-segments: wipe `ListingIndex` and `SearchIndex` independently and confirm the actor's UI (conversation view, search results) is indistinguishable from before the wipe once rebuilt — asserting the observable outcome rather than the rebuild mechanism.

## Open questions carried forward

- Exact grace-window duration (30 days proposed as a default, should be configurable) — a tuning parameter, not a design fork.
- Whether `space-chat-openmls` and `space-chat-storage-redb` share one physical `redb::Database` file or use separate files — a composition-time decision for `space-chat-app`, not a core design question.
- Eager vs. lazy attachment fetch policy remains deferred to the app-shell/UX design (sub-project 5), per the protocol spec.
